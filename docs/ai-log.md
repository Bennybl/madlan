## Caught a bad AI answer: real Grok credentials, example question wrongly rejected

## Feature: a general, bounded answer surface instead of one hardcoded capability at a time

The user asked a reasonable follow-up question through the live site — "bring me the most expensive and cheapest apartment from all the cities you have" — and got back a hard-coded refusal: "the system only provides historical statistics (transaction count, median price, median price per m²) and cannot show specific apartments as most expensive or cheapest." The first instinct was to add `CheapestDealId`/`MostExpensiveDealId` fields one at a time. The user correctly pushed back: "you cannot expect to know future questions; it should be built such that you can ask any question and the LLM will build the query that answers it." Fixing this by hardcoding another field would have reproduced the exact problem on the next question.

The real constraint, restated to the user before building: the architecture deliberately never lets the LLM write or execute SQL, so "any question" has to mean "any question answerable from a fixed, auditable menu of operations," not literally arbitrary querying. The user agreed to the proposed shape: expand `DealFilters` to cover the dataset's other columns (floor, year built, condition, source, has-elevator/parking/balcony/safe-room), and add a `QueryMetric` enum (count, plus min/max/average/median of price, price per m², size, rooms, floor, year built) that the LLM selects by name. Each metric maps to one fixed, parameterized SQL statement chosen by a C# switch (`SqliteDealRepository.DescribeMetric`); the LLM only ever picks which pre-vetted statement runs, never composes query text. Min/Max also return the specific matching deal's ID, so an answer can actually name it.

Wired the metric choice through every stage: `QueryGenerationOutput.Metric` (a string, parsed via `Enum.TryParse` and rejected the same way malformed output is rejected elsewhere if it doesn't match an allowed name), `QueryVerificationService` now verifies the metric choice alongside the filters, `MadlanApplicationService.AskAsync` passes it to `QueryService.Query`, and `CalculatedEvidence` includes the requested metric/value/deal ID in what the summary and result-verification stages see, and in the known-deal-ID set so referencing that specific deal is never flagged as a hallucination.

Three more real problems surfaced while verifying this live against the actual API, none of which a fake-provider test would have caught:

1. **Enums serialized as raw integers.** The first live response showed `"metric":4` instead of `"MaxPrice"` — ASP.NET Core's default JSON formatter renders enums as their underlying number unless told otherwise. This silently broke the new UI code, which matched on the string name. Added a global `JsonStringEnumConverter` in `Program.cs`'s `AddJsonOptions`, and the same converter for `CalculatedEvidence.ToJson` so the evidence text shown to the LLM stages is equally readable ("MaxPrice", not "4").
2. **Query-verification rejections were in English**, the same Hebrew-message gap already fixed in the generation prompt but missed in `QueryVerificationService` and `ResultVerificationService` when they were written in steps 9 and 11. Added the same explicit "message must be Hebrew" instruction to both.
3. **The heavier, more detailed prompts needed more time.** With the full filter/metric menu spelled out, real Grok calls started exceeding the 30-second per-stage timeout fairly often (not rare transient slowness — repeated failures across consecutive attempts). Raised `Llm.TimeoutSeconds` to 60, `Llm.ServerTimeoutSeconds` to 240, and the browser `ASK_TIMEOUT_MS` to 250000, and updated the architecture's documented deadlines accordingly. A full four-stage round trip now takes roughly 60–105 seconds in this environment.

Also fixed, while testing: the "ask" flow left the submit button and textarea enabled and gave no visible progress indicator while a question was being processed, so a user could submit the same question multiple times in a row or not know whether anything was happening. Both the question form and the manual-filter form now disable their submit control (and the question textarea) for the duration of the request and re-enable it in a `finally`, guarded by the same request-token check used elsewhere so a stale request can't re-enable controls a newer request already disabled.

Added UI support for the new per-question metric: a fourth metric card appears only when `result.requestedMetric` is present, labeled from a fixed Hebrew dictionary keyed by the enum name, showing the value (currency-formatted for price-based metrics) and the specific deal ID for Min/Max.

## Feature: React chat UI, plus full details for single-item answers

Two more pieces of user feedback after testing the metric feature live: first, asking for one specific item (the cheapest/most expensive apartment) returned only a value and a deal ID, when the expectation was the full record; second, the plain HTML/JS page should look and behave like a CRM chat widget — a simple "thinking" indicator while a question is processing, and the chat clears up once the answer lands. The user was asked directly whether the chat redesign should stay vanilla JS/CSS (no new build step, consistent with the architecture's original "plain HTML/CSS/JavaScript" decision) or move to React; they chose React, so this is a deliberate architecture reversal, not a default choice.

## Feature: Nth-ranked metrics ("the second most expensive"), instead of opening raw SQL generation

The user hit two more real gaps in the same session: "the second most expensive city" (nonsensical for this dataset -- the system ranks deals, not cities, so this was correctly rejected with an honest Hebrew explanation) and "the second most expensive apartment in every city" (a real, answerable gap -- "second most expensive" is an ordinal/ranked question the metric menu had no way to express, since Min/Max only ever return the single most extreme matching deal). The user's instruction was explicit and broad: the system should answer *any* question about the data, the query-generation LLM should be given the filter/field list and build whatever query answers it, and -- if needed -- it could even be allowed to emit raw SQL, provided there was a deterministic mechanism to stop it from doing damage.

Chose not to take the raw-SQL route. The specific gap -- "Nth highest/lowest value" -- is a narrow, well-defined extension of the Min/Max metrics that already exist, not evidence that the bounded-menu design has run out of room: `DealQuery` gained `RankedMetrics` (`RankedMetricRequest { QueryMetric Metric, int Rank }`), restricted to the existing Min/Max-style `QueryMetric` values via a new `QueryMetrics.Rankable` set (derived from the enum's own `Min`/`Max` naming convention, not duplicated by hand). `SqliteDealRepository` computes a ranked metric with the identical parameterized `ORDER BY` query already used for a plain Min/Max, just adding `LIMIT 1 OFFSET (rank-1)`; the sort column and direction still come from the fixed C# switch over the enum, never from a string the model controls, and the only attacker/model-influenced value (the integer rank) goes through a parameterized SQLite `$offset`. This answers "the second/third/Nth most expensive/cheapest X" with the exact same guarantee the rest of the system already has -- zero new injection surface, fully auditable, no new attack class to defend -- versus raw LLM-generated SQL, which even with careful guardrails (a read-only connection, a statement allowlist, query-timeout/row-limit caps, banning multiple statements) is a fundamentally larger and harder-to-fully-close surface for a gap this narrow. This is a deliberate judgment call on the user's explicit "if you think raw SQL is needed, you can, but be careful" instruction: it was not needed here, so it was not used.

The generation prompt now describes ranked metrics directly: a rankable metric list (just the Min/Max subset), the `{metric, rank}` pairing, and the rule that rank 1 duplicates the plain metric (so "the most expensive" stays a plain `MaxPrice`, while "the most expensive *and* the second most expensive" needs both a plain `MaxPrice` and a ranked `MaxPrice` rank 2). Verification got the same addition to its prompt and now rejects a proposal missing a ranked metric the question asked for, using the wrong rank, or ranking an Average/Median/TransactionCount metric (impossible, rejected at generation time already, but checked again here for defense in depth). The result-summary prompt was told how to describe `rankedMetrics` entries, naming the rank and the specific deal. The UI (`ResultMetrics.jsx`) renders a metric card per ranked result using a new `describeRankedMetric(metric, rank)` label builder in `format.js` (e.g. "המחיר היקר ה-2 ביותר") and auto-expands that specific deal's full detail the same way a plain Min/Max result already does.

## Feature: group-by ("per city", "per property type"...), and a verification-prompt wording bug it exposed

The user escalated sharply after the ranked-metric feature: "I tried to ask a question and could not get an answer... the system must support any question regarding the data... I repeat any." The concrete trigger was the same recurring pattern as several earlier entries -- "the second most expensive apartment *in every city*" -- which the ranked-metric feature alone couldn't answer, because it still computes one global answer, not a per-category breakdown. This was the actual missing primitive underneath several previous "known limitation" notes in this log (the city-breakdown gap, the "is the data segmented by city" confusion): the system had no way to compute anything *per group*.

Built `GroupByField` (City, Neighborhood, PropertyType, Condition, Source, Rooms, Floor, YearBuilt) and threaded it through the same path as metrics and ranked metrics: `DealQuery.GroupBy` -> `SqliteDealRepository.ComputeGroups`, which runs the existing per-metric `(expression, condition, aggregation)` triples (the exact same ones `ComputeRequestedMetric`/`ComputeRankedMetric` already use) through `GROUP BY`/`PARTITION BY` SQL instead of a single aggregate -- Min/Max per group use a `ROW_NUMBER() OVER (PARTITION BY <column> ORDER BY <expression> ...)` window function so a ranked metric ("second most expensive") also works *per group* ("second most expensive in each city") in the same query shape. The group column name comes from one more fixed enum-driven switch, never from model text; the dataset's small size (23 cities, 100 neighborhoods, 6 property types -- all comfortably under the 200-group cap added as a defensive bound) keeps this cheap. This was the same judgment call as the ranked-metric feature: the user again explicitly offered raw LLM-generated SQL as an acceptable fallback, and again a bounded, deterministic extension to the existing menu covered the actual question asked with no new injection surface, so that's what was built.

## Fix: two real bugs that silently dropped valid group-by summaries

The user reported a concrete failure: "מה מחיר דירה ממוצעת בכל עיר ומה החציון?" (average and median apartment price per city) correctly computed the right data -- 23 per-city groups with average and median price each -- but came back with "סיכום מאומת אינו זמין כעת" (verified summary unavailable) every time. Temporarily added debug logging around the summary/verification try/catch (removed before committing) to see exactly where it failed, rather than guessing.

Two distinct, real bugs surfaced:

1. **`ResultSummaryService`'s own evidence-citation check was too strict for aggregate-only group breakdowns.** The rule "a non-empty result's summary must cite at least one real deal ID" makes sense for a flat answer (there's always a contributor-deal list to point to) and for any Min/Max/ranked metric (there's a specific matching deal to name). But a per-city breakdown of *averages and medians only* has no single deal that represents a city's average price -- citing an arbitrary deal ID from the unrelated top-level contributor-page list would be fabricating a false link, and the model correctly declined to do that, which tripped the "did not reference any supporting evidence" exception on every attempt. Fixed by adding `CalculatedEvidence.HasDealAnchoredMetric(result)` (true when any requested/ranked metric, overall or within any group, has a `dealId`) and only requiring a citation when either `GroupBy` is unset (preserving the original, still-correct behavior for flat queries) or such an anchored metric actually exists. Added prompt wording telling the model explicitly that an aggregate-only group breakdown may legitimately have empty `referencedDealIds`, so it stops being asked to prove something that isn't true.

2. **`ResultVerificationService` sometimes rejected a fully correct summary because of the already-known, already-documented Tel Aviv spelling fragmentation** -- the debug trace showed one rejection with the message "הסיכום מכיל שמות ערים כפולים... (כגון תל אביב-יפו פעמיים)" ("the summary contains duplicate city names... like Tel Aviv-Yafo twice"), even though the two "duplicate-looking" entries were two different, genuinely distinct raw strings in the data (`תל אביב-יפו` and `תל אביב - יפו`, different spacing/hyphenation -- part of the same locality-fragmentation issue documented since the typo-resolution work). The verification model had no way to know this was expected rather than an error, so it flagged a correct, complete summary as wrong. Added the same explanation already used elsewhere in this log to the verification prompt: two similar-looking `groupValue` entries are each a real, distinct value actually present in the raw data, and must never be rejected as a "duplicate."

Added unit tests for both: `ResultSummaryServiceTests` (`Summarize_allows_empty_references_for_a_group_by_breakdown_with_only_aggregate_metrics` and `Summarize_still_requires_a_reference_for_a_group_by_breakdown_with_a_ranked_metric`, confirming the citation requirement is relaxed only when there is truly nothing to cite) and `ResultVerificationServiceTests` (`Verify_tells_the_model_not_to_reject_similar_looking_group_names_as_duplicates`, confirming the explanation reaches the prompt). The Docker .NET test suite passed all 91 tests (3 new).

## Feature: outlier/anomaly detection per field, optionally per category

The user asked for apartment-price outliers "that don't converge to a normal distribution" per city, and got the honest-but-unhelpful answer that the system only computes historical statistics and can't identify outliers or test normal-distribution fit. Unlike the previous two asks (ranked metrics, group-by), this genuinely needed a new statistical primitive -- nothing in the existing metric menu could flag an individual deal as unusual relative to its peers.

Implemented IQR-based outlier detection (`DealQuery.OutlierField`, one of Price/PricePerSqm/SizeSqm/Rooms/Floor/YearBuilt), combinable with the existing `GroupBy` so outliers can be computed independently per city/property-type/etc. `SqliteDealRepository.ComputeOutliers` computes Q1 and Q3 within each partition using the same nearest-rank percentile SQL pattern already proven for the median, then flags any deal below `Q1-1.5×IQR` or above `Q3+1.5×IQR` (the standard Tukey fence) -- fully parameterized, the group column and metric expression both coming from fixed enum-driven switches, same pattern as every other deterministic-menu feature in this project. Capped at 200 returned outliers as a defensive bound (the dataset's small size makes this generous, not tight).

Deliberately corrected a mismatch between what the user asked for and what is actually implemented: the user's phrasing ("don't converge to normal distribution") describes a formal normality test (e.g. Shapiro-Wilk), which is a materially different, more complex statistical procedure than distance-based outlier flagging. Rather than silently building the narrower IQR version and calling it what the user asked for, every layer that explains this feature -- the generation prompt, the verification prompt, the summary prompt, and the UI's visible copy -- states plainly that this is a standard distance-based outlier rule, not a normality test, and never claims one was performed. The generation prompt does treat "find outliers/anomalies" phrased in terms of normal-distribution fit as a match for this feature rather than rejecting it outright, since in practical terms that is what the user is actually asking for (find the unusual values), but the system is explicit with the user about which of the two it actually computed.

Hit one real SQL bug while implementing the grouped case: the window functions in the `Ranked` CTE used `PARTITION BY {partitionColumn}` with the *raw* column name (e.g. `City`), but that CTE operates over an intermediate `Measured` CTE that only exposes the value under its own alias, `GroupValue` -- `City` doesn't exist there, so every grouped outlier query failed with `SQLite Error 1: no such column: City`. Fixed by partitioning on `GroupValue` unconditionally (it's a literal `NULL` for the ungrouped case, which SQLite correctly treats as one partition, so no branching is needed between grouped/ungrouped SQL text for this clause).

Also caught, before committing, a wrong test assumption of my own: an initial test asserted the dataset's known low-price anomaly (deal D100317, ₪18,000) would always be flagged as a price outlier. It wasn't, and that's mathematically correct, not a bug -- with no property-type filter, the full price range is wide and right-skewed (a ₪15M+ deal exists in the same sample), which pushes Q3 and the IQR high enough that the IQR method's lower fence goes negative; no real (non-negative) price can be a "low" outlier under that fence for this particular unfiltered sample. This is a known, well-documented limitation of the IQR method on heavily skewed distributions, not specific to this implementation. Replaced the test with one that checks the general mathematical property (every returned outlier is genuinely outside its own bounds, bounds are internally consistent) rather than asserting a specific deal must appear.
