# Madlan Deal Explorer - Architecture

Status: revised on 2026-10-05. Steps 1-12 are merged; step 13 is under review. Later steps are planned work.

## 1. Product

Build one public Hebrew RTL page where a CSM can ask about the supplied property transactions, see calculated statistics and inspect the records behind them. Manual filters remain available when the LLM fails.

The [challenge](madlan_rnd_ops_engineer_challenge.md) and [CSV](madlan_deals_sample.csv) are the sources of truth. This document replaces earlier architecture recommendations, including those in `madlan_architecture_proposal.md` and `product_guiede.md`.

Scope: explore the supplied dataset and explain its numbers. Load it into in-memory SQLite at startup. No data upload, admin area, authentication, persistent database, separate import pipeline, rate limiting, usage quotas or historical-version system. No valuations, forecasts or external data.

## 2. Simple application structure

Use one C# ASP.NET Core application serving a compiled UI from `wwwroot`, plus one xUnit test project. Use .NET 10, CsvHelper and Microsoft.Data.Sqlite, with direct SQL and no ORM. Build with Docker when the local SDK is unavailable; the inspected machine has .NET 8 only.

The UI started as plain HTML/CSS/JavaScript in steps 12-13 and was rebuilt as a React app (Vite, under `src/MadlanExplorer/client`) once the chat-style question experience needed richer client-side state (message history, a thinking indicator, per-message result rendering) than hand-rolled DOM manipulation could keep maintainable. `npm run build` compiles it into `wwwroot`, which is generated and gitignored, not committed. The Docker build adds a `node:20-alpine` stage that runs this build and copies its output into the `wwwroot` used by `dotnet publish`, so the published image is unchanged: one self-contained ASP.NET Core container serving a static UI and the `/api/*`/`/healthz` endpoints, no Node runtime needed after the image is built.

Keep three application components:

| Component | Responsibility |
|---|---|
| Dataset loader | Read the CSV once at startup and populate in-memory SQLite with raw, normalized and queryable report/deal data |
| Query service | Validate filters, construct provider-neutral query semantics, and call the deal repository |
| Deal repository | Translate a provider-neutral query into parameterized database commands and return results/evidence pages |
| Question workflow | Generate and verify structured filters, then summarize and verify calculated results using independently configured models |

Flow: browser -> ASP.NET Core controller -> application service -> query service -> deal repository -> database. The single application service orchestrates manual requests now and will coordinate the LLM stages, query service and repositories for natural-language requests. The query service validates filters and builds a provider-neutral `DealQuery`; it never contains provider SQL. `IDealRepository` translates that query into fixed parameterized commands for its provider. Database filtering, conflict exclusion, aggregation, median calculation and pagination prevent request code from loading a full result set into application memory.

Keep ordinary classes in one application project. `QueryService` depends only on `IDealRepository`; it does not know which database implementation is registered. `SqliteDealRepository` supports the demo. Do not implement a PostgreSQL repository, add a PostgreSQL package, or configure a PostgreSQL connection in this project. The repository contract, typed query/result objects, and provider-neutral service semantics make a future PostgreSQL adapter straightforward to add. Isolate LLM provider calls behind one small interface so tests can supply stage responses. Keep workflow orchestration in an ordinary class; use a stage parameter and configuration instead of separate provider implementations for each model.

## 3. Runtime data loading and correctness

Bundle the CSV with the application, outside `wwwroot`. At startup, create an in-memory SQLite database, read and normalize the CSV, then insert all reports in one transaction before accepting requests. Keep the database read-only at the application level after loading. Changing the file requires restarting/redeploying the app; there is no reload service.

Use two tables: `Reports` (row ID, deal ID, original field JSON, normalized field JSON and quality flags) and `Deals` (deal ID, conflict status, canonical report ID and indexed query columns when usable). Retain every source row. Preserve JSON for evidence, but store filter and metric fields in typed columns: city, neighborhood, property type, rooms, date interval, price, size and supplied price per m². Add indexes matching the supported filters and evidence pagination. Keep dataset hash and coverage as application metadata.

The demo uses shared in-memory SQLite because the supplied CSV has 530 rows. Treat it as a repository implementation, not a production capacity target. A future production adapter can use PostgreSQL with typed `numeric`, `date` and text columns, the same query semantics, migrations, pooled connections and database-side median/aggregate queries. This repository does not implement that adapter. Do not use SQLite JSON scans, C# full-result materialization or unbounded contributor ID lists for large data. Return aggregate values plus a paginated evidence page; retrieve more evidence by cursor. Keep provider-specific SQL inside the relevant future repository implementation.

Use `Data Source=Madlan;Mode=Memory;Cache=Shared;Pooling=False`. Keep one keeper connection open for the application's lifetime and open separate short-lived connections for requests; do not share a connection object across concurrent requests. Dispose the keeper at shutdown. This preserves the database between requests without creating a disk file. See [Microsoft's in-memory SQLite guidance](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/in-memory-databases).

If the file is missing or structurally unreadable, stop startup with a clear log message. Individual missing or questionable field values become warnings. Compute a file hash for identifying the dataset in results and logs; this is just an identifier, not a version-management system.

The supplied file has 530 rows, 520 deal IDs, six exact duplicate pairs and four conflicting IDs: D100017, D100124, D100032 and D100303. It also has 26 month-only date rows, missing values, a zero price and an NIS 18,000 price.

Apply these explicit rules:

- Normalize whitespace, numeric formats, room suffixes and supported boolean values. Preserve missing values as unknown.
- Extend `NormalizeCity(string value)` using the bundled official locality catalog: prefer exact Hebrew/English matches, then conservative typo matching. Define and test a minimum similarity and a minimum gap from the next candidate before enabling automatic correction. Ambiguous or weak matches retain the original city and receive a quality flag; never choose a tied candidate. Use the same resolver for question filters, requesting clarification when needed. No LLM calls during CSV loading. `QueryGenerationService` calls this resolver on the LLM's proposed `city` filter before execution: a confident correction (exact or typo) replaces the value, an ambiguous match returns a clarification response, and an unresolved value is executed as given rather than silently dropped, matching the eventual zero-result or quality-flagged outcome CSV loading already produces for the same name. This closes a gap where this document already specified reusing the resolver for question filters but no code path actually did so. A known limit this does not fix: the catalog's official name for Tel Aviv is `תל אביב - יפו`, far enough (edit distance) from the short form `תל אביב` that neither a typo of the short form nor the short form itself resolves to it — the same reason the dataset already contains three distinct, un-merged Tel Aviv spellings (`תל אביב`, `תל אביב - יפו`, `Tel AvivYafo`) from CSV loading. Fixing this would mean either loosening the conservative typo threshold (risking false-positive corrections elsewhere) or adding a name-equivalence rule, which this project deliberately removed earlier (see the "refactor: use only official locality names" decision) in favor of catalog-only matching with no alias overrides.
- Preserve both original and normalized data. Keep untouched `RawJson`, normalized fields, and locality resolution metadata (official code, original value, resolved value, exact/typo/unresolved status and rule version). Show corrections in evidence details. Rebuild normalization at startup; no additional persistent store is needed.
- Group by deal ID. Count identical normalized reports once, retaining all source rows. Compare business fields including reported source. Exclude conflicting groups from metrics and keep them inspectable; do not choose a winner.
- Parse ISO, day/month/year, dot-separated dates and English month/year. Preserve month precision as an interval. Include a month-only date in a date-filtered query only if the whole month is inside the range; explain partial-overlap exclusions.
- Support city, neighborhood, property type, room minimum/maximum, date range, floor minimum/maximum, year-built minimum/maximum, condition, source, and the booleans has-elevator/parking/balcony/safe-room. Filters combine with AND; omitted filters impose no restriction. A specific room count, floor, or year-built means minimum and maximum are both set to that value. Require clarification for an ambiguous neighborhood.
- `propertyType` is a closed, exactly-6-value set in the supplied data (בית פרטי, דופלקס, דירה, דירת גג, דירת גן, פנטהאוז), not a free-text field, and the common word "דירה" (apartment/flat) is itself one of those exact values rather than a generic term a model might reasonably treat as implicit/skippable. `QueryGenerationService` and `QueryVerificationService` both inject the dataset's real, exact `GetDatasetFacts().PropertyTypes` list into their prompts and require the filter whenever the question names or implies one of those exact categories, the same enumeration-not-prose pattern already used for the `QueryMetric` menu above. This followed repeated real failures where a question naming "דירה" was rejected (generation step) for omitting `propertyType` despite the word being right there in the prompt -- prose instructions alone ("set propertyType when the question implies a category") were not reliable; handing the model the literal, closed list removed the ambiguity.
- Count non-conflicting deals that definitely satisfy the filters. Missing filter values cannot be treated as matches.
- Calculate median price from positive prices, and median price per m² from individual positive-price/positive-area ratios in database SQL. Missing area excludes only the latter metric. Use database-native exact numeric handling where available and round only for display, to the nearest shekel, midpoint away from zero.
- Return null for an empty metric. Show each metric's contributing count and a paginated evidence page, plus relevant exclusions and reasons.
- Beyond the three headline metrics, support any number of additional requested statistics per question (`DealQuery.Metrics`, a list), each chosen from an allow-listed `QueryMetric` enum (count; min/max/average/median of price, price per m², size, rooms, floor, or year-built), computed by a fixed parameterized SQL statement selected in C# by a switch over the enum. The LLM only ever picks *which* allow-listed statistics to compute, by name, as a JSON array; it never writes or composes SQL, and there is no cap on how many it lists (each is a cheap, independent, pre-vetted query against a 530-row dataset). A question asking for more than one statistic at once -- "average and median price" -- returns one `RequestedMetricResult` per metric, not a rejection. Min/Max also return the specific matching deal's ID so the answer can name it (e.g. "the cheapest apartment is deal X at ₪Y"). This keeps "answer any question about the data" bounded to a closed, auditable, extensible menu rather than open-ended query generation; it started as a single metric per question and was generalized to a list once a real compound question ("average and median") showed the single-metric design couldn't answer it.
- An Nth-highest/lowest question ("the *second* most expensive apartment", "the *third* cheapest") is answered the same bounded way, via `DealQuery.RankedMetrics` (`RankedMetricRequest { Metric, Rank }`): `Metric` must be one of the existing Min/Max-style `QueryMetric` values (`QueryMetrics.Rankable`, derived by filtering the enum names for the `Min`/`Max` prefix, not a hand-maintained duplicate list) -- Average/Median/TransactionCount have no single Nth matching deal and are rejected as a ranked choice at generation time. `Rank` is a plain positive integer (1 = the same deal the plain metric would return; validated to the range 1-1000 in `QueryService`, defense-in-depth repeated in `SqliteDealRepository` by rejecting a non-Min/Max aggregation before building SQL). The repository computes it with the exact same `ORDER BY <column> {ASC|DESC}` used for the plain Min/Max query, just with `LIMIT 1 OFFSET (rank-1)` added -- direction and column both come from the fixed enum-driven switch, never from interpolated user input; only the integer offset is attacker/model-influenced, and it goes through a parameterized `$offset`, never string-concatenated. This was added after the user asked for "the second most expensive apartment per city" and proposed, as one acceptable option, letting the query-generation LLM emit raw SQL with deterministic injection guards; a bounded Nth-rank extension to the existing metric menu answers the same class of question with no new attack surface at all, so it was built instead of opening raw SQL generation.
- A per-category breakdown question ("the cheapest apartment *in every city*", "average price *per neighborhood*", "count *by property type*") is answered via `DealQuery.GroupBy` (a single `GroupByField`: City, Neighborhood, PropertyType, Condition, Source, Rooms, Floor, or YearBuilt -- the dataset's discrete/categorical columns, reusing the same column names as the existing filters). When set, `SqliteDealRepository` computes every requested plain and ranked metric *per distinct value of that column* instead of once overall, using `GROUP BY`/`PARTITION BY` SQL built from the same fixed per-metric `(expression, condition, aggregation)` triples already used for the ungrouped case -- the group column name comes from one more fixed C# switch (`DescribeGroupByColumn`), never from model-controlled text. The result (`DealQueryResult.Groups`, one `GroupedQueryResult` per distinct value actually present, capped at 200 groups) sits alongside the existing overall/ungrouped numbers, which are still computed unconditionally -- grouping adds a breakdown, it does not replace the headline answer. This directly resolves the "no city breakdown" gap noted in earlier entries (the user had been told, correctly, that no such grouping existed yet); it was not built via raw SQL generation, for the same reasoning as the Nth-rank extension above.
- An outlier/anomaly question ("which apartments are outliers per city", "values that don't fit the typical pattern") is answered via `DealQuery.OutlierFields` (a list drawn from the six numeric fields: Price, PricePerSqm, SizeSqm, Rooms, Floor, YearBuilt -- a question can check several fields, or "every field," at once), optionally combined with `GroupBy` to compute outliers independently within each group. `SqliteDealRepository.ComputeOutliers` uses the interquartile-range (IQR/Tukey) rule: within each group (or the whole filtered sample when ungrouped), compute Q1 and Q3 via the same nearest-rank percentile technique already used for the median, then flag every deal whose value falls below `Q1 - 1.5×(Q3-Q1)` or above `Q3 + 1.5×(Q3-Q1)`. This is a standard, distance-based, distribution-agnostic outlier rule -- it is explicitly **not** a formal statistical test of normality (e.g. Shapiro-Wilk), and every layer that describes it (generation prompt, verification prompt, summary prompt, UI copy) says so plainly, since a user could reasonably ask for "normal distribution" testing and the honest answer is that this system flags unusual values by range, not by fitting a distribution. The result (`DealQueryResult.Outliers`, each entry tagged with the `OutlierField` it was found under, capped at 200 rows per field) lists each flagged deal's value and the group's fence (`LowerBound`/`UpperBound`) it fell outside. As with ranked metrics and group-by, this was built as a bounded deterministic extension rather than opening raw SQL generation, which the user again explicitly offered as an acceptable fallback.
- `propertyType` is not the only filter whose dataset has a small, closed set of real values the model would otherwise have to guess: `condition` and `source` get the identical treatment (`DatasetFacts.Conditions`/`Sources`, injected into both the generation and verification prompts). This mattered in practice: a multi-word condition value meaning "new, from the contractor" was being misread by the model as two separate things (a condition plus an unrelated "contractor" source) until it was handed the literal, closed list, the same fix already proven for `propertyType`.
- `GroupByField` also covers the four boolean amenity columns (HasElevator, HasParking, HasBalcony, HasSafeRoom), computed exactly like the other group-by dimensions; a boolean group's `GroupValue` comes back as the literal SQL value ("1"/"0"), humanized to Hebrew כן/לא only at the display layer (UI and the result-summary prompt), not in the data itself.
- A prompt that names a specific deal ID (the dataset's `D` + six digits format) is answered by a small, fully deterministic shortcut in `MadlanApplicationService.AskAsync` that runs *before* any LLM call: a regex match against the prompt, then a direct `IDealRepository.GetDeal` lookup. A real ID returns status `"deal"` with just the ID (the client reuses the same `DealDetailCard` component the manual deal-lookup panel already uses, via a fetch to `/api/deals/{id}`); an ID-shaped token that isn't in the dataset returns `"unsupported"` with the same `DealNotFound` message the manual lookup panel uses. This bypasses query generation, verification, summary, and result-verification entirely -- zero LLM involvement, zero new risk -- because the question "what does this specific, already-named deal look like" has nothing left to interpret or verify once the ID is extracted.
- A question comparing two or more specific named values of the same dimension ("compare Tel Aviv and Jerusalem", "penthouse vs. garden apartment", "with parking vs. without") is answered by setting `groupBy` to that dimension and leaving the matching filter unset -- grouping already computes every value of the dimension separately, including the ones named, so there is no need for (and no way to express) a filter restricted to just the compared subset. This guidance has to be stated to *both* the generation and the verification prompts independently; adding it to only one left the other stage free to reject a now-correct proposal on its own, now-outdated assumption that a named city/property type always requires a matching single-value filter.
- A question phrased as "show me" / "list" / "give me all" the transactions matching some filter (rather than asking for a specific statistic) is still a normal, fully supported query: the filters are set as usual and metrics are left empty, since the transaction count plus the sample's own contributing deal IDs already serve as that list. Like the comparison guidance above, this had to be added to both the generation and verification prompts, for the same reason.
- The chat is a stateless, single-turn API by design (section 4): each `/api/ask` call carries no server-side memory of earlier turns. This broke the "ask for clarification" flow in practice: when the server asked which field to check outliers in and the user replied "every field," that reply alone, sent with zero context, was meaningless and correctly (if unhelpfully) rejected as unsupported. Fixed client-side rather than by adding server-side session state: `ChatPanel` detects when the previous assistant turn was a `clarification` and, before sending the next message, combines the original question, the clarification question asked, and the user's new reply into one self-contained prompt (the chat still displays exactly what the user typed; only the text sent to `/api/ask` is enriched). This keeps the server's stateless, auditable, one-shot-per-request design intact while making multi-turn clarification actually work.
- Preserve the supplied price per m² and flag differences greater than max(NIS 1, 1% of the computed ratio).
- Flag positive prices below NIS 100,000 but keep them eligible. Exclude zero/negative prices from price metrics. Warn when a metric has fewer than five contributors. These warning thresholds are documented heuristics.

**Superseded by the agent loop below.** The bullets above (metric list, ranked metrics, group-by, outlier fields) described the system's query model through several rounds of incremental, bounded extensions -- each one solved a real reported gap, but each also required a new enum, a new prompt paragraph describing it, and a new switch arm in the repository, duplicated across the generation prompt, the verification prompt, and the C# code. After enough rounds of this (and one compound question -- "the cheapest apartment among the five most expensive cities" -- that no single-shot combination of these mechanisms could express at all, since it needs one query's result to decide the next query's filter), the user asked for a structural change: stop growing the schema per question shape, and instead give the model one small, generic primitive plus the ability to use it more than once per question, observing real results between calls. See the end of section 4 for what replaced this. The historical bullets above stay as a record of why the generic primitive looks the way it does (it has to express everything they did), not as the current request/response shape.

Results describe this sample, not the housing market as a whole. A source label is a value in the CSV, not independent verification.

## 4. LLM and HTTP interface

**Current design: a bounded agent loop over one generic query primitive**, replacing the earlier four-stage single-shot pipeline described further below (kept for its reasoning, not as the current behavior).

The query model is one generic shape, `DataQuery`: the same `DealFilters` as always, an optional `GroupBy` (one discrete dimension: City, Neighborhood, PropertyType, Condition, Source, Rooms, Floor, YearBuilt, or one of the four boolean amenities), an `Aggregate` (Count, Average, Median, Min, Max, or Outliers), an optional `Field` (Price, PricePerSqm, SizeSqm, Rooms, Floor, YearBuilt -- required for every aggregate except Count), a `Rank` (which Nth extreme value, for Min/Max), and an optional `Limit`/`Descending` (when grouped, narrows to the top/bottom N groups by their computed value). This one shape expresses everything the earlier per-question-shape mechanisms did -- a plain metric, an Nth-ranked value, a per-category breakdown, a top-N selection, an outlier scan -- without a separate enum or prompt paragraph per shape. `SqliteDealRepository.ExecuteDataQuery` still builds fixed, parameterized SQL from enum-driven column/expression switches for every branch; the model never supplies SQL text, only values for these fields, exactly as before.

`QueryOrchestrationService.RunAsync` answers a question by looping, up to 10 iterations: ask the model for one action (query, final, clarification, or unsupported); if it asks for a query, execute it deterministically and feed the real `DataQueryResult` back as part of the next prompt; repeat. A compound question such as "the cheapest apartment among the five most expensive cities" takes two iterations in practice -- one grouped query to find the top-5 cities by a price measure, one broader grouped query (deliberately *not* filtered down to those five, since no such multi-value filter exists) to get every city's cheapest apartment, and the model itself picks the minimum among just the five it already identified when composing its final answer. This is the model doing a join over two bounded, deterministic results it has already seen, not a third query primitive -- it needed no new backend capability at all, just the ability to call the first primitive twice and reason over both real answers before concluding.

No per-step verification happens inside the loop: each step is pure parameterized computation, not a claim, so there is nothing to double-check until the model actually asserts something. Only the finished answer (the `final` action) is checked: a deterministic C# pass rejects it outright if it names a deal ID that was never returned by any gathered query in this conversation (the same hallucinated-reference guard used throughout this project, just generalized from one `DealQueryResult`'s known IDs to the union across every step), and then one LLM call (`LlmStage.Verification`) sanity-checks the candidate against the gathered evidence, the same role `ResultVerificationService` played before. A rejection at either point falls back to showing the gathered steps with no summary and a "verified summary unavailable" message, exactly like the old summary-stage failure path -- the data is still real and worth showing even when the prose describing it isn't trusted.

If the model still has not produced `final`/`clarification`/`unsupported` after 10 iterations, the loop stops and returns `unsupported` with a message asking the user to simplify the question, rather than looping forever or guessing.

| Config | Role |
|---|---|
| `Llm.Models.Agent` | Called once per loop iteration: propose a data query, or conclude. Used repeatedly per question, so the fast/cheap model is the right default -- the loop's own self-correction (it sees each real result before deciding the next step) compensates for an occasional fast-model misstep far better than a single expensive call with no chance to recover ever could. |
| `Llm.Models.Verification` | Called once, at the end, to sanity-check the finished answer against everything actually gathered. |

This is a deliberate trade against the earlier design, where the one upfront interpretation step used the slowest, most capable model because it had no later chance to recover from a mistake. Here, *every* step has a later chance to recover (the next iteration, or the final grounding check), so paying for the best model only once no longer makes sense; paying for speed throughout does, since the same question may now cost several model calls instead of one.

Define an `ILlmProvider` interface that accepts a stage, its configured model ID, structured input and cancellation token; workflow code depends only on this interface. Start with a `GrokLlmProvider` adapter selected through configuration, with Grok credentials kept in server-side secrets. Keep Grok HTTP details, authentication and response parsing inside that adapter so a future provider can implement the same interface without changing the workflow, query or API code. Record stage and model ID in request diagnostics. Verification is an additional check, not a guarantee of correctness: shared C# validation and deterministic calculations remain mandatory.

Reject malformed model output. No automatic repair loops or retries beyond the agent's own iteration budget. Unsupported prompt requirements must not be silently dropped. Treat prompts and dataset text as untrusted data in every call.

The application service owns the `/api/ask` workflow. It calls the LLM stages, query service and repository without exposing those internal operations as public endpoints. Return bounded evidence in the final response.

Step 7 originally narrowed the public surface to `/api/ask` alone. Step 12 reinstates `/api/query`, `/api/dataset` and `/api/deals/{dealId}` as thin, deterministic, LLM-free reads because the product brief and this document both require manual filters to keep working when the LLM is unavailable (section 1, section 5) — that guarantee has no meaning without a non-LLM request path for the UI to call. These three endpoints never touch `ILlmProvider`; they call `QueryService`/`IDealRepository` directly, the same way `MadlanApplicationService.AskAsync` does once a query is approved.

Use configurable deadlines: 120 seconds per model call, 600 seconds for the complete server workflow, and 620 seconds for the browser. The server/browser deadlines were raised specifically to accommodate the agent loop's worst case (up to 10 Agent calls plus one Verification call); in practice most questions resolve in 1-3 iterations and finish in 15-60 seconds, since both configured models are the fast tier (see above) -- the generous ceiling exists for the compound questions that genuinely need several steps, not as the typical case. Propagate cancellation and stop the loop after a failure. No automatic retries beyond the agent's own iteration budget. Invalid model output, refusal, timeout or outage produces a clear Hebrew message and leaves manual filtering available. Handle missing API credentials the same way. There is no application rate limiter, quota store or concurrency limiter. Retune these values again after deployment if production latency differs from this development environment's, or if a different model is configured.

Keep credentials on the server. Validate request fields and render untrusted text safely. Errors have a request ID, stable code and plain Hebrew message. Log that ID, dataset hash, filters, duration and error category; never log secrets. No separate monitoring service is needed.

A 10-iteration loop has 10x the chances for one LLM call to return something unparseable compared to the old single-shot design, so `QueryOrchestrationService` treats a malformed/unexpected response at *any* iteration as a soft failure, not a hard one: it stops the loop and shows whatever steps were already gathered (`status: "query"`, no summary, a plain Hebrew message) rather than a raw 500 -- the real computed data from the steps that did succeed is still worth showing even when one step didn't. The one thing that still hard-fails with no data shown at all is a genuine grounding violation on the *final* answer -- a missing summary, or a cited deal ID that was never actually returned by any gathered query -- since that is the one case where showing something could mean showing a fabricated claim.

The LLM-based final-answer verification (`LlmStage.Verification`) is treated as a confidence signal, not a second hard gate: a grounded candidate (every cited deal ID genuinely present in the gathered evidence) is always shown, even if this check rejects it, fails to parse, or the call itself errors -- in that case the summary is shown together with a short Hebrew caveat explaining why confidence is lower, rather than hidden outright. This followed a real user complaint that a correctly-grounded answer was being replaced with a bare "verified summary unavailable" and nothing else; the deterministic grounding check (not the LLM check) is the one actually protecting against a fabricated claim, so it is the one allowed to withhold the answer entirely.

A compound question needing an Nth-ranked value (N > 1) combined *across* several specific named categories as one merged ranking -- e.g. literally "the fifth cheapest apartment among the five most expensive cities," one ranking over their combined deals, not five separate per-city answers -- cannot be computed with the generic `DataQuery` primitive: nothing restricts to exactly that combined category set, and an ungrouped ranked row carries no category label to check it against. This is a real, narrower limitation than the already-solved rank-1 case ("the cheapest apartment among them"), which the same two-query pattern (a grouped query to find the categories, then an unfiltered grouped Min/Max query to read the answer off just the ones that qualify) answers correctly. The agent prompt explicitly distinguishes the two, by name, so a rank-1 question isn't mistakenly treated as the unsupported rank-N>1 case -- an earlier, less precise version of this guidance caused exactly that regression during testing, briefly rejecting the already-working rank-1 pattern.

## 5. UI, deployment and delivery

One RTL page contains a question input, examples, editable filters, three metric cards, a supporting-record table and expandable record details. Show sample sizes, warnings, data coverage and calculation definitions. Show the verified Hebrew summary above its evidence, and show original/normalized locality values and correction status in report details. Display progress through interpretation, verification and summary stages. Show empty/error states explicitly; a failed new question must not make old results look current.
